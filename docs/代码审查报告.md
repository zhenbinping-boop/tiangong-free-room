# 天津工业大学空教室查询网站 — 代码审查报告

**审查对象**：`tiangong-free-room/crawler/fetch_rooms.py`、`parser.py`、`.github/workflows/daily-crawler.yml`
**审查方式**：静态代码审查 + 对目标系统的实际网络探测（取证）
**核心症状（用户描述）**：登录后获取的 cookie 多次失效或过快过期，无法持续获取真实数据

---

## 结论先行

**"cookie 失效" 是表象，不是根因。**
经实测验证：该项目的登录流程**从未成功建立过有效会话**。代码把认证指向了错误的身份系统（CAS），而 CAS 明确拒绝为 jwxs 教务系统签发票据；jwxs 真实的登录入口是它自己的 Spring Security 端点，且强制要求图形验证码 —— 代码对此零处理。因此每一次运行都认证失败，静默降级到**硬编码的假数据生成器**。

网站现在展示的 42 间教室（教室号/容量/类型）与代码里硬编码的 `BUILDING_ROOM_TEMPLATES` **逐字 100% 吻合**，仅"占用节次"随机 —— 这就是铁证：**线上从来没有抓到过一条真实数据。**

---

## 一、问题诊断

### 1.1 取证事实（均为实测，非推测）

| # | 事实 | 证据 |
|---|------|------|
| F1 | **线上数据是伪造的** | `public/data/today.json` 42 间教室与代码 `BUILDING_ROOM_TEMPLATES`（22+20=42）的教室号、容量、类型**完全一致**；真实系统不可能与硬编码模板逐字相同 |
| F2 | **CAS 拒绝 jwxs 作为合法服务** | `GET https://pt.tiangong.edu.cn/cas/login?service=https://jwxs.tiangong.edu.cn/...` → 返回 200 页面，内容为 **"未认证授权服务 — 不允许使用CAS来认证您访问的目标应用"** |
| F3 | **jwxs 有独立登录，不走 CAS** | `GET http://jwxs.tiangong.edu.cn/gotoLogin` → 302 → `https://jwxs.tiangong.edu.cn/login`；表单 `POST /j_spring_security_check` |
| F4 | **jwxs 登录强制图形验证码** | 登录页字段：`lang`、`tokenValue`(动态)、`j_username`、`j_password`、`j_captcha`；验证码 `/img/captcha.jpg` 实测返回 180×60 JPEG，内容 4 字符带干扰线（本次抓到 "3D2X"）；页面加载 `md5.min.js`、`sm3/*.js`（国密） |
| F5 | **CAS 自身登录也有验证码 + 密码加密** | `pt.tiangong.edu.cn/cas/login` 含 `authcode` 验证码字段、隐藏真实 `password` 字段（由 JS `CreateRatePasswdReq()` 填充）、可见 `ppassword` 是假字段、`uuid`、超长 `execution` token |
| F6 | **会话 Cookie 形态** | `JSESSIONID` + `student.urpSoft.cn`（两者同值），HttpOnly、**会话级**（无过期时间）→ 失效由服务端空闲超时控制（此类强智/URP 系统典型 30 分钟） |
| F7 | **`updated_at` 是 UTC，不是北京时间** | `today.json` 的 `updated_at: 2026-09-09 02:54:50` 与该次 commit 的 `2026-09-09T02:54:50Z` **完全一致**，证明是 runner 的 UTC 时钟 |
| F8 | **失败被静默掩盖** | `build_today_json()` 抓取失败 → 静默生成假数据；脚本退出码恒为 0；workflow 永远绿色 |

### 1.2 四个审查维度的具体问题

#### ① 登录流程 — 结构性不可用

- **认证目标错误**：`login()` 对 `pt.tiangong.edu.cn/cas/login` 发起登录，但该 CAS 的服务注册表中没有 jwxs（F2）。**这个分支在结构上就注定失败，无论账号密码多正确。**
- **密码提交为明文**：`login_data["password"] = self.password`。CAS 真实页面要求 JS 加密后的值（F5）；jwxs 侧则需确认是否 md5/SM3（页面加载了相关 JS）。明文提交必然失败。
- **验证码零处理**：jwxs 的 `j_captcha`、CAS 的 `authcode` 都没有任何获取/识别/回填逻辑（F4、F5）。
- **`tokenValue` 未处理**：jwxs 登录表单有动态 `tokenValue`，代码从未获取。
- **登录成功判定是假阳性**（`fetch_rooms.py:138-143`）：
  ```python
  if "登录失败" in login_resp.text or "密码错误" in login_resp.text:
      return False
  print("... CAS Authentication successful!")
  return True
  ```
  只要响应页面没出现这两个词就算成功。CAS 返回"未认证授权服务"页面时不含这些词 → **判定成功，实际连票都没发**。从未真正验证过会话可用。

#### ② Cookie 管理机制 — 三处硬伤

- **有效性判定不可靠**（`fetch_rooms.py:81`）：
  ```python
  if test_resp.status_code == 200 and "gotoLogin" not in text and "login" not in text:
  ```
  `"login"` 作为子串几乎出现在所有页面（JS 路径 `loginOut`、CSS、文案等）→ 大量**误判**；而有些登录页本身返回 200 → 也会**漏判**。用"页面里有没有 login 字样"判断鉴权状态，方向就错了。
- **手写 Cookie 头与 Cookie Jar 冲突**（`fetch_rooms.py:70`）：`self.session.headers["Cookie"] = self.cookie` 直接写死请求头。此后服务器 `Set-Cookie` 下发的新 cookie 会被 requests 写进 jar，但请求头里的旧值优先级更高 → **服务端刷新的会话永远用不上**，会话"看起来"就特别容易失效。
- **从不持久化 / 从不回写**：cookie 从环境变量读入，登录成功后也不把新会话写回存储。每次运行都是冷启动 + 重新登录（且登录必失败）。
- **全局请求头污染**：`X-Requested-With: XMLHttpRequest` 设在 Session 级，连 CAS 登录页的 GET 也带上了，可能导致 CAS 走 AJAX 分支返回不同内容；`Referer/Origin` 固定为 jwxs 域名，发给 CAS 属于跨站伪造头。

#### ③ 会话有效性 — 根本原因（见第二节）

- 会话是**服务端空闲超时**控制（F6，典型 30 分钟），代码无任何心跳/保活。
- **GitHub Actions 出口 IP 每次随机**，与手工取 cookie 时的浏览器 IP 不一致；强智类教务系统常做 **IP 绑定**，跨 IP 的会话直接判无效。
- **并发登录冲突**：手工脚本（用户本机 IP）与定时任务（runner IP）若用同一账号，服务端若有单会话策略会互踢。
- **时区错误导致查询日期错一天**（F7）：workflow cron `0 19 * * *` UTC = 北京时间次日 03:00，runner 时钟是 UTC，`datetime.date.today()` 取到的是北京视角"昨天"的日期 → 查的是昨天的空教室。

#### ④ 错误处理 — 健全性极差

- **静默 mock 兜底掩盖一切失败**：抓取失败 → 生成以日期为种子的随机"占用"数据 → 写入 today.json → exit 0。网站照常"更新"，**用户与维护者都看不到真实报错**。
- `--real` 参数只在日志里 WARNING，不影响退出码，workflow 不会红。
- 8 个端点盲试（CAS 与 WebVPN 混扫、字段名 `roomName/r/jsmc` 逐个猜）属 spray-and-pray，极易触发 WAF/限流/账号锁定，也说明**从未抓到过真实响应结构**。
- `int(item.get("capacity", ...))` 未做类型/空值防护，脏数据会直接抛异常。
- WebVPN 路径（`vpn.tiangong.edu.cn/https/6a77...`）是另一套独立认证体系，混在一起只会增加噪声。

## 二、根因分析

按权重排序，四个根因共同构成了"cookie 老是失效"的完整因果链：

### R1（决定性）：认证目标与协议完全错误

代码向 `pt.tiangong.edu.cn` 的 CAS 发起登录，但该 CAS **明确拒绝**为 jwxs 这个 service 认证（实测返回"未认证授权服务"）。而 jwxs 的真实登录入口是它自己的 `POST /j_spring_security_check`。

> **结论：不是"cookie 容易过期"，而是"从来就没有成功建立过会话"。** 用户观察到的"失效"，本质是每次运行都拿不到有效会话，然后静默降级到假数据。

### R2：验证码完全未处理

jwxs 登录强制 4 位图形验证码（实测存在，绑定会话）；CAS 登录页同样有 `authcode`。代码对验证码零处理 —— 即便把端点改对、密码改对，也会在验证码这一关被挡下。**这使得"自动登录"在当前实现下不可能成立，只能依赖人工粘贴 cookie，而人工 cookie 又必然过期。**

### R3：手工 Cookie 的生命周期与运行环境错配

即使手工从浏览器粘贴一份真实有效的 cookie，它也注定短命：

| 因素 | 说明 |
|------|------|
| 会话级 Cookie | `JSESSIONID`/`student.urpSoft.cn` 无过期时间，失效由服务端空闲超时控制（典型 30 分钟） |
| IP 不一致 | GitHub Actions 出口 IP 随机，与浏览器取号 IP 不同；强智类系统常做 IP 绑定 → 跨 IP 即失效 |
| 无心跳 | 长时间不访问 → 空闲超时踢出 |
| 不回写 | 服务端即便续期/换了会话，代码也用不上（手写 Cookie 头压制了 Set-Cookie） |
| 并发冲突 | 手工脚本与定时任务同账号在不同 IP 登录，单会话策略下互踢 |

### R4：静默 mock 兜底让失效彻底不可见

失败 → 假数据 → exit 0 → workflow 绿 → 网站时间戳照常更新 → **唯一的症状就是"数据看起来不太对/cookie 又失效了"**，真实错误被系统性隐藏，导致团队一直在表层症状（换 cookie、加 Referer、改 hex 编码）上打转 —— git 历史里一连串 `fix: sanitize Cookie header`、`add Referer and Origin headers`、`update WebVPN hex encoding` 正是这种"治标不治本"的痕迹。

## 三、解决方案

### 阶段 0：先止血（半天可完成，让失败可见）

1. **移除/改造静默 mock**：`generate_fallback_records()` 仅在显式 `--allow-mock` 时启用，生产默认关闭。
2. **失败必须非零退出**：真实抓取失败 → `sys.exit(1)`，workflow 据此变红，可加钉钉/邮件/Server 酱通知。
3. **数据打上来源标记**：`today.json` 增加 `"source": "live" | "stale" | "mock"`；前端非 `live` 时显示醒目横幅"当前数据非实时（更新于 X，本次更新失败）"。
4. **保留最后一次真实数据**：失败时不要覆盖成假数据，而是保留旧文件 + 标记 `stale`。
5. **修时区**：workflow 中设置 `TZ: Asia/Shanghai`，或代码内用 `zoneinfo.ZoneInfo("Asia/Shanghai")` 计算"今天"与 `updated_at`。当前实现查的是昨天的数据、显示的是 UTC 时间。

### 阶段 1：实现对的真实登录（jwxs 原生，替换 CAS 分支）

**彻底删除 CAS 分支**，新建 `JwxsClient`：

```python
# 伪代码骨架
1. s = requests.Session()
2. s.get("https://jwxs.tiangong.edu.cn/login")     # 拿 JSESSIONID + student.urpSoft.cn
3. html = 上一步响应; tokenValue = re.search(r'name="tokenValue" value="([^"]+)"', html)
4. img = s.get("https://jwxs.tiangong.edu.cn/img/captcha.jpg?<rand>")   # 必须同一 Session
5. code = ocr(img)                                  # 见下
6. s.post("/j_spring_security_check", data={
       "lang": "zh", "tokenValue": tokenValue,
       "j_username": user, "j_password": pwd, "j_captcha": code,
   }, headers={"Referer": "https://jwxs.tiangong.edu.cn/login"})
7. assert s.get(受保护页) 未重定向到 /login          # 真正验证登录成功
```

- **验证码识别**：推荐 `ddddocr`（对这类强智 4 位验证码识别率高）。设置信度阈值 + 重试循环（失败就 `refreshCaptcha` 换一张，上限 N 次）。
- **密码是否需加密**：`login.js` 本身无加密逻辑，`j_password` 可能为明文；但页面加载了 `md5.min.js`、`sm3/*.js`。**不要猜 —— 先用浏览器 DevTools 抓一次真实登录请求，看 payload 里 `j_password` 到底是明文还是哈希，再照抄。**
- **使用 Session 的 cookie jar，绝不要再手写 `Cookie` 请求头**，让服务端下发的 `Set-Cookie` 生效。

### 阶段 2：登录态的自动化维护（可持续稳定的关键）

1. **Cookie 持久化**：登录成功后把 `s.cookies` 落盘为 `cookies.json`（含时间戳、生成时 IP）；下次运行**先校验、有效则复用** → 大幅减少验证码消耗与登录次数。
2. **校验逻辑重写**：`is_valid()` = 请求真实数据接口，判定 `HTTP 200` + 响应符合预期 JSON 结构。**永远不要用"页面里有没有 login 字样"来判断鉴权状态。**
3. **心跳保活**：若部署在常驻环境（校园内网机器 / VPS / 自建 runner），每 ~10 分钟请求一次轻量鉴权接口，对抗 30 分钟空闲超时。
4. **失效自动重登**：校验失败 → 走完整登录（含验证码 OCR）→ 重试；设重试上限，连续失败则告警而非继续用假数据。
5. **IP 一致性（最关键的一条）**：让爬虫运行在与"取号环境"一致的网络里。优先级：
   - **最佳**：校园网内的自建 GitHub Actions runner / 宿舍常开电脑 / 树莓派 + crontab
   - **次佳**：完全跑在校内机器，跑完把 `today.json` push 到仓库
   - **避免**：用 GitHub 托管 runner 做鉴权（出口 IP 每次随机，跨 IP 会话大概率被判无效）
6. **单会话约束**：只用一个账号、一个"会话所有者"。不要手工脚本和定时任务在不同 IP 同时登录同一账号。

### 阶段 3：数据正确性与架构收尾

1. **停止 8 端点盲试**。先用浏览器正常登录一次，DevTools 抓到真实的空教室接口 URL + 请求体 + 响应 JSON，**把解析器写成针对那个确定 schema**，而不是猜 `roomName/r/jsmc`。
2. `buildingId` 别名 `"1"/"2"` 大概率不对，以抓包为准。
3. 确认接口的日期语义：强智系统常按"学年学期 + 周次 + 星期"查询，而非自然日；`term` 硬编码 `"2026-2027-1"` 也需随学期自动推进。
4. 控制频率：一天 1 次足够；若需更高时效，用"常驻 + 心跳 + 定时抓取"，而非高频重登。

### 验收标准

- [ ] 连续 7 天 `today.json` 的 `source` 均为 `live`，`updated_at` 为北京时间
- [ ] 人为将 cookie 置为无效后，系统能自动重登并恢复，无需人工干预
- [ ] 抓取失败时网站明确提示"数据非实时"，而非展示编造数据
- [ ] workflow 在失败时变红并发通知

## 附：合规与稳健性提醒

- 使用真实学号自动登录属个人数据查询范畴，请控制频率（建议 ≤1 次/日）、单线程、加随机抖动，避免对教务系统造成压力或触发账号锁定。
- 凭据只放 GitHub Secrets / 本地环境变量，不要写进代码或数据文件（当前做法正确，请保持）。
- 若学校后续接入统一 CAS 并放开 jwxs 的 service 注册，CAS 分支才有重启的价值 —— 届时也必须补齐验证码与密码加密逻辑。
